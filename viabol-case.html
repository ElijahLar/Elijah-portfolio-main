Viabol

Making business automation understandable without a workflow builder.

Viabol is a lightweight automation product for small service businesses. It turns recurring tasks such as quote follow-up into guided, reviewable workflows—without asking users to build automations from nodes, triggers, or field mappings.

The case at a glance

Problem

Automation tools often make the user design the system.

Triggers, nodes, field mappings, and error paths create work before the user reaches the business task.

Product bet

Start from the task, then keep every important action reviewable.

Templates reduce setup work while clear states and history make the automation easier to trust.

My scope

Product direction, UX/UI, copy, architecture decisions, and final build.

I used Codex for code support and debugging, then reviewed and adapted the work before shipping.

Current state

Working production product; activation and paid value still need validation.

I separate what is already real from the claims I have not earned yet.

Design challenge

Automation is difficult to trust because most of it happens out of view.

I reviewed existing workflow tools and tested real automation runs during development, paying particular attention to failure states and the risk of sending messages to someone else’s customers.

How might I let someone set up, approve, and trust an automation without making them learn the engine behind it?
01

Actions happen out of view

People need a clear record of what happened and when.

02

Emails reach real customers

A wrong follow-up can damage an existing relationship.

03

Success is not one state

Accepted, scheduled, delivered, and failed cannot look identical.

04

Flexibility adds work

A blank canvas makes the user design the automation system themselves.

Core product decision

Templates instead of a blank canvas

Tools such as Zapier and n8n are powerful because users can build almost anything. I deliberately accepted less flexibility so Viabol could ask less from the user up front.

Direction dropped

Build the workflow yourself

Choose triggers, actions, connections, mappings, conditions, and error paths.

Benefit
Almost anything is possible.
Cost
The user has to design the system.

Direction kept

Choose the business task

Pick a template, finish a short setup, test it, and review the result.

Benefit
Less to understand before reaching value.
Cost
Viabol supports fewer use cases.

Product principle: expose the decision the user needs to make, not the machinery required to execute it.

Interaction design

Making quote follow-up reviewable

A quote can be entered directly or imported from a business-owned Google Sheet. Both paths create something to review; neither path silently schedules or sends anything.

  1. 01

    Entered or imported

    The quote comes from Viabol or the connected spreadsheet.

  2. 02

    Owner reviewed

    The owner checks the details, message, tone, and delay.

  3. 03

    Scheduled

    Nothing moves forward until the owner chooses when it should run.

  4. 04

    Engine accepted

    A run exists, but Viabol does not call it delivered yet.

  5. 05

    Delivered or failed

    The final outcome stays visible in the history.

Designing for trust

Trust had to appear in the flow itself—not just in landing-page copy.

Review before action

Importing data never sends an email. Scheduling always requires a clear choice.

Precise status language

An accepted request is separated from confirmed delivery and failure.

Readable recovery

The error explains what failed, while the original run stays available.

Traceable history

The input, result, engine response, and timeline can be checked later.

≠

Engine accepted is not delivered.

A technically successful handoff is not presented as customer delivery. That distinction required more state design and logging, but prevents misleading success messages.

Behind the interface

The simple setup hides a real multi-step workflow.

The underlying system receives the quote, waits for the selected delay, drafts the message, sends it, notifies the owner, and records the result.

Interface

Next.js · React · Tailwind CSS

Turns the workflow into a task people can set up, review, schedule, and follow.

Product data

Supabase Auth · Postgres · Row Level Security

Keeps records separated by account and protects connection details behind server-side access rules.

Automation & services

Activepieces · OpenAI API · Google Sheets · Resend · Stripe

Runs the workflow, drafts content, imports familiar data, sends email, and handles billing states.

Delivery & measurement

GitHub · Coolify · Self-managed VPS · GA4

Supports controlled deployment and rollback, while analytics load only after consent.

Iteration without fake before screens

What changed as I built it

I did not preserve polished screenshots of every early version, so I show the decisions, reasons, and trade-offs instead of reconstructing a false process story.

01

Direct entry became two paths

Started with entering each quote inside Viabol.

Changed to keeping that path while adding a business-owned Google Sheet for recurring lists.

Trade-off less typing, but another connection to maintain.

02

Email extraction stayed experimental

Explored forwarding sent quotes to an inbox so Viabol could extract the details.

Held back because uncertain fields added risk before the core review flow was proven.

Trade-off a spreadsheet feels less automatic, but is easier to understand and recover.

03

Success became several states

Problem an engine accepting a job does not mean the customer received the email.

Changed to separate scheduling, engine response, confirmed delivery, and failure.

Trade-off more state design and logging, but fewer misleading success messages.

Evidence and next step

A working product, not a finished success story

The most credible version of this case separates what exists in production from the product value I still need to validate.

What is real today

  • The product is public and works in production.
  • Direct quote entry and optional Google Sheets intake both work.
  • Imports create something to review; they do not send an email.
  • Scheduled, accepted, delivered, and failed are distinct states.
  • A failed run keeps its error details when someone retries.

The next validation

  • Watch five service businesses explain the product in their own words.
  • See whether they can finish setup and understand each state without help.
  • Test whether review creates enough trust to justify the extra step.
  • Measure whether the task is useful often enough to pay for.

What I would not do yet

Add more templates before the current activation flow is clear without me explaining it.

Reflection

Simplifying automation is not mainly about hiding controls.

It is about making every action, status, and failure understandable enough for someone to trust the system with a real customer relationship.
